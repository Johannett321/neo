---
title: One odd file no longer stops the rest
date: 2026-09-09
---

A fix for 1.6.0, and the second half of one.

A recording segment that captured nothing is a real thing to find in a data
folder: a file of zero bytes, pointed at by a real row. Until 1.6.0 it went up
without anybody noticing, because encrypting it added a nonce and a tag and
nothing was ever truly empty on the wire. With the encryption gone it arrived
as what it is, and the sync server refused it — under the message for a file
that is too *large*, which is the opposite problem and sends you looking in
entirely the wrong place.

Worse than the refusal was what followed it. Neo treated a rejected file as a
failure of the whole pass rather than of that one file, so a single empty
segment stopped **every** icon, avatar and recording behind it from syncing at
all, and the pane said only that some file was too big.

## What changed

- **A file the server will not take is skipped, and the rest still go.** That
  was already true of being out of space — one oversized recording was never
  allowed to block the icons behind it — and it is now true of any file the
  server refuses. It will refuse the same file next time; that is no reason to
  stop.
- **An empty file syncs as an empty file.** Your other Mac ends up with exactly
  what this one has, which is the whole job.
- **The two refusals say different things**, so "too large" means too large.

Both halves are covered by tests that fail without the fix: the sync test now
pushes an empty file alongside a real one and insists both arrive.
